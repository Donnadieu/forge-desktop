# Decisions

Answers to the plan's open questions (section 11). Each is the default the build uses until the owner
says otherwise.

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Triage in Linear is a per-team switch, not a status | Setup turns the team's Triage switch on through the API (`teamUpdate triageEnabled`). If Linear refuses, it creates a plain "Triage" column instead and says so. | Uses Linear's own Triage when it can; never blocks setup. |
| 2 | The key Forge makes | An SSH signing key (ed25519). The private half lives only in the Keychain and reaches git through the Mac's ssh-agent; only the public half is on disk. Registering it on GitHub changes the person's account, so the app asks first. Own GPG key and "unsigned, with a warning" stay as the other two choices. | SSH keys are the simplest to register on GitHub; the agent keeps the private half off disk. |
| 3 | GitHub sign-in for V1 | Reuse the `gh` sign-in already on the Mac. No GitHub App registration. | No account changes, nothing to register. |
| 4 | Who it's for | V1 runs on the owner's Mac. Public release stays possible (signing, notarization, updater) but isn't built for. | Ship the smallest thing that works. |
| 5 | The Linear key for agents | The Linear tools agents get carry a `${LINEAR_API_KEY}` placeholder that the agent's own environment fills, so no key is written into a card's folder. | Plan section 2: secrets only in the Keychain and the engine's environment. |
| 6 | Basecamp sign-in | Basecamp's device sign-in (a short code approved in the browser) with the public client Basecamp's own command-line tool uses (`basecamp-cli`); scope full. Tokens only in the Keychain; the engine and agents ask the app for a short-lived token (`Forge --basecamp-token`). | No password box and no client secret to ship; the access token lasts about an hour, so one renewer under a lock keeps a replaced refresh token from being used twice. |
| 7 | GitHub Issues as a tracker | A GitHub project (v2) is the board: its Status field gives the columns, issues carry assignees, labels and comments, and "Closes owner/repo#N" links the pull request. Signed in with GitHub's device sign-in and the public client GitHub's CLI uses (`FORGE_GITHUB_CLIENT_ID` can name another app), scopes `repo read:org project`; the token only in the Keychain. Setup asks to turn off GitHub's project automations that set Status. | Forge has no GitHub tracker to port; `gh`'s sign-in on the Mac usually lacks `project`, and asking the person to change `gh` would touch every tool using it. Built-in automations moved a card from Human Review back to In Progress in the live test. |
| 8 | Several accounts per intelligence provider | `store.json` holds small tables (trackers, projects mapped to one repo, accounts) with ids; each project has one intelligence provider and one account. `setup.json` stays the running project's working copy, so every screen and the engine read what they read before. Secrets stay in the Keychain, one item per account; a browser account signs in inside its own login folder (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) under Forge's `accounts/`. Settings from 0.2.16 carry over: each Keychain item already there becomes an account under its old name, nothing copied. | JSON like the rest of Forge's settings beats adding SQLite for four tables and one writer. The Claude Code sign-in Forge keeps is a long-lived token, so accounts never share a login; an account without one points Claude Code at its empty folder and fails as signed out instead of quietly using the person's own login (checked live: "Not logged in"). |
| 9 | Workspaces, step 1 | `store.json` version 2 adds workspaces, several connections per tracker kind (each its own Keychain item), Forge's own GitHub accounts and a project list per workspace; one project runs at a time and switching stops it. A project's answers are kept whole in its record while another runs (`ProjectRecord.choices`). | Keeping each project's full `SetupChoices` lets every screen and the engine stay as they are (they read `setup.json`); one engine per project and running several workspaces at once are the next steps (design doc). |

## Missing columns, parking, Next step and skills (Nov 11, 2026)
Plan: [missing-columns-and-skills](../exec-plans/active/missing-columns-and-skills.md). Decided while building, without stopping to ask (Omar's rule for this goal).

| # | Question | Decision | Why |
|---|---|---|---|
| 10 | Which columns does setup still require? | Backlog, Todo, In Progress and Done. Triage, AI Review, QA, Human Review, Rework and Merging are optional. | Without those four there's nothing to pick up and nowhere to finish; ATC Rewrite has exactly these plus Triage. |
| 11 | Rework was "always on" | Rework becomes optional like the others: unavailable when its column is missing, still not switchable off by hand. | ATC Rewrite has no Rework column; the Studio keeps its old rule for boards that have one. |
| 12 | Where the decision log lives | This file (`docs/design-docs/decisions.md`), not a new `docs/decisions.md`. | The repo already has one decisions file linked from the docs map. |
| 13 | How the engine learns a card is parked | The agent writes `.forge/parked` in the card's folder (git-excluded); the engine reads it when the turn ends and records it in `forge.sqlite`. | Text-first: the lead's routing note says when to park, and a file is something the engine can check without new agent tools. |
| 14 | "Nothing the team can see" | At the parking moment Forge posts no comment and moves nothing. The card's workpad comment, written during the build as before, is unchanged (Workflow Studio's "What others see" governs it). | Parking itself must be invisible; changing how workpads work is outside this round. |
| 15 | Next step on a stage that's off by choice | Still offered. | Picking it is the person asking for that step now. |
| 16 | How the engine knows a board's columns | Linear: the team's states, read live (cached 5 minutes). Basecamp and GitHub: the columns setup mapped, so a column added there shows after setup reads the board again. An empty list guards nothing. | Linear can be asked cheaply; the other two keep their column ids in the workflow file already, and reading them live would need new API calls for a rare event. |
| 17 | A column appears or disappears while Forge runs | The app saves the new columns and restarts that project's engine (agents pause and pick their cards back up, as after a Workflow Studio save). | The engine reads its stages once at start; a restart is the existing, tested way to change them. |
| 18 | "The next stage has no column" | Cards skip a missing stage when a later column exists (QA missing: AI Review → Human Review). They park only when no column comes after before Done. | Moving to the next column that exists keeps the board useful; parking is for boards with nowhere left to go. |
| 19 | Next step with no column on a card Forge doesn't work (Human Review, Backlog) | Refused with a plain line ("Forge runs QA here only on cards in Todo or In Progress."). A stage with a column still moves any card. | Forge only dispatches cards in its active columns; on a shared board every parked card is In Progress, so the case that matters works. |
| 20 | Which agent runs a step picked with no column | The agent of the card's column (In Progress's role), told which step to run. | Roles pick by column; the card never leaves In Progress, and a one-off role switch would need engine changes for a rare case. |
| 21 | How skills are found and kept fresh | The app reads them (no engine change): `<folder>/<skill>/SKILL.md` only, a plain file (never a link), from the repo's `.claude/skills`, `.agents/skills`, `.codex/skills`, `.cursor/skills`, `skills`, then `~/.claude/skills`, Codex's `skills`, then Forge's bundled ones; the first name wins. Each folder is re-read only when its date or a SKILL.md's date changes, checked when the list opens. | The session's folder is on this Mac; checking dates on open is cheap, exact and needs no watcher thread. |
| 22 | Running a skill | Claude Code's own skills (repo `.claude/skills`, `~/.claude/skills`) are sent as `/<name>`; any other is sent as "Use the <name> skill: read <its SKILL.md> and follow it." | Claude Code only registers those two folders; the agent can read any other SKILL.md when told where. |
